anvilproject/galaxy-tests · experiment runs of 7 and 9 November 2026

Running the AnVIL tool tests with and without GCP Batch

Three ways to run Galaxy jobs were compared: the nightly configuration (one Batch VM per job), everything on a single 32-vCPU head node, and Batch with a warm pool of reusable VMs. First on the 1433 tool tests, then on 108 real tools over 2 GB of sequencing data, submitted as one user and as four at once. The single node is the cheapest and, for one user, the fastest. Batch is what scales: four users cost it 10% more wall-clock, where the single node needed 60% more and its Galaxy buckled. The warm pool costs more in every experiment without making anything faster.

Executive summary

Two experiments. The tool tests (7 November) run 1433 tiny jobs; the tool matrix (9 November) runs 108 real tools on 2 GB inputs, once as a single user and once as four users at the same time.

  • With real jobs and one user, the single node wins on both time and money. The 108-tool matrix took 77 minutes and $2.24 on the no-Batch node against 99 minutes and $3.41 on Batch and 94 minutes and $5.37 on the warm pool. Half of the gap is the NFS tax below.
  • With four users at once, only Batch holds its pace. Batch finished four copies of the matrix in 110 minutes, 10% longer than one copy, for 3.4 times the money. The single node had completed 90% of the work after 179 minutes when its Galaxy became unreachable, and its queue wait tail reached 45 minutes against 7 on Batch. Per user, the node is still cheaper: $1.30 against $2.90.
  • Batch jobs pay an NFS tax that grows with load. Every Batch VM reads its inputs from the head node over NFS. CPU-bound aligners run as fast there as on the node, but tools that stream a 2 GB file run 1.7 to 4 times slower, and slow a further 1.5 times when four users share the head node: fastqc takes 110 s on the node, 414 s on a Batch VM, 608 s on a Batch VM with four users.
  • A single node is the cheapest way to run the suite. The no-Batch run cost $5.51 against $12.77 for the nightly and $16.52 for the warm pool, and the model keeps it at 45 to 60% of the nightly's cost as tool runtimes grow by up to 100 times.
  • Batch is the faster option once tools run long. The single node is bounded by its slowest test and takes 8.6 hours at 10 times today's runtimes against 4.6 for the nightly. At today's runtimes it was 45 minutes slower than the nightly.
  • Tool execution is 10 to 12% of Batch VM time. About four hours of tools ran inside 24 to 34 VM-hours; the rest is boot, idle and teardown. Half the tool jobs finish in a second or less.
  • The warm pool costs 40 to 57% more than plain Batch on real jobs too. At TTL 600 s with 4 idle VMs it reused a third of the matrix jobs and cut the median queue wait by 15 to 20 s, while idle VMs added 5 to 10 VM-hours per level. Same wall-clock, more money.
  • On the tool tests, the warm pool cannot save money and at its current settings does not save time either. Jobs are shorter than a VM boot, so idle VMs cost more than they avoid. TTL 600 s with 4 idle VMs would reuse about 73% of jobs and shorten the test step by roughly 20 minutes for about $12.50 more per run.
  • Two operational problems surfaced. GPU tests on the warm pool hung for 110 minutes because g2-standard-32 capacity was exhausted in both us-east4 zones, and the orphan-cleanup step will delete another run's Batch VMs if two runs overlap.
  • Test coverage held. Each configuration ran the same 1433 tests, with 5 new flye failures on the single node from its memory limit and a net 11 fewer failures on the warm pool's image.

Real jobs: 108 tools on 2 GB inputs

The tool tests measure Galaxy's scheduling and Batch's VM boot, because half of their jobs finish in a second. To see the configurations on work a user would actually submit, 114 single-tool jobs covering 108 of the 260 tested tools were run as a dependency graph over the 2 GB tier of the benchmarking inputs: paired reads from a whole-genome, an RNA-seq and a ChIP-seq experiment. Five aligners, the samtools and picard chains, five variant callers and the bcftools suite, peak calling, deeptools, quantification, and the text utilities on everything's reports. The whole graph was submitted once (one user) and then four times at once (four users), on each configuration, on fresh instances.

Two things the matrix exposed

The single node had been running with a quarter of its cores. The nightly values give Kubernetes jobs a CPU request of a quarter core per TPV core so that small jobs fit on the head node's spare CPU, and Galaxy's Kubernetes runner sets a tool's thread count from that request. On the no-Batch branch every tool runs as a Kubernetes job, so bwa_mem had been running with 2 threads instead of 8, STAR and freebayes with 3 instead of 10. Every no-Batch number before 9 November 12:00 UTC, including the 7 November tool-test run and the first 2 GB workflow run, carries that handicap; bowtie2 took 125 minutes there against 32 on Batch. The no-batch mixin now requests the full core count, and the matrix figures above are from runs with it.

Galaxy on the single node stopped answering under four users. After 179 minutes of the four-user level, with about 30 jobs still queued behind the core cap, the head node's Galaxy web process lost its message-queue connection and refused API connections for several minutes. It recovered on its own, but the experiment driver gave up in the meantime. Batch head nodes carry the same Galaxy on a smaller VM and never faltered, because their job execution, and its memory and I/O, happens elsewhere.

What broke on the way, and what changed

Getting these numbers took four rounds of runs on 9 November. Each round found a defect in the test harness or the deployment that is now fixed in galaxy-tests or the galaxy-k8s-boot branches.

  • A 19.3 GB default disk quota on every image paused all jobs once the 2 GB inputs and the first alignments exceeded it. The benchmark workflow raises it to 400 GB before staging.
  • The orphan-cleanup step deleted other runs' Batch jobs. It removed every active Batch job in the project created after its own run began. Three finishing runs wiped out level one of two runs deployed 30 minutes later. It now deletes only Batch jobs that the instance's own Galaxy lists as queued or running.
  • Cancelling a run orphaned its VM and Batch jobs. GitHub cancelled the workflow step but an always()-gated step started the matrix, and the run was then killed before cleanup. Head node and about 30 Batch jobs had to be removed by hand. Matrix and summary steps are gated on !cancelled() now, and runs are left to fail rather than cancelled.
  • An empty workflow input is not empty. GitHub substitutes the default, so a run meant to skip the workflows ran them. The benchmark caller takes an explicit none.
  • A GitHub incident at 05:59 UTC returned 504 on release downloads and slowed the container registry; three deployments failed fetching the NFS provisioner chart. Transient, nothing to fix.
  • Tool-level failures that count as findings: MultiQC 1.35 exits 0 but prints a temp-directory traceback that Galaxy's stderr rule marks fatal, on every image; bwa_mem2 has no human index in the CVMFS data; two of 435 warm-pool jobs lost their stdout file on a reused VM; one of four samtools fastx pods died at its 4 GB memory limit name-sorting a 2 GB BAM.

GPU tests never ran on the warm pool

All five image_learner tests hung for 110 minutes and then failed. Cloud audit logs show why: creating the g2-standard-32 VM failed with ZONE_RESOURCE_POOL_EXHAUSTED in both us-east4-a and us-east4-c, 18 attempts over the whole period. Batch never reported the VM as running, so the pool's claim timeout never fired and the harness waited until its own limit. The same tests pass in the nightly on the CPU destination in 13 to 26 minutes. The GPU tail added about 25 minutes to the warm pool's test step; its last non-GPU test finished 12 minutes before the step ended.

Warm pool settings

The run used TTL 120 s and 2 idle VMs per machine shape per handler. 141 of 751 Batch jobs reused a VM, 19%, with reused jobs finishing in 38 s median against 125 s fresh. To find better settings, the run's actual job arrivals were replayed through a pool model at other TTLs and sizes. The model reproduces the observed cost at the current settings within a cent, though it is optimistic on reuse (29% against 19%), so the reuse figures are upper bounds.

The pool cannot save money on this workload because the jobs are shorter than a VM boot. What it buys is latency: each reused job skips about 78 s. At TTL 600 s and size 4 the model reuses 73% of jobs and avoids 12 boot-hours, worth roughly 20 minutes off a 150 minute test step across 32 slots, for about $12.50 more per run. Beyond that point reuse barely improves while cost keeps climbing. Pool size is per shape and this run spread jobs over 11 shapes, so size 4 can mean up to 44 idle VMs at a peak.

Recommendations

  1. For one user, or for cost, run on a single node. It is the cheapest configuration in every experiment and, once its jobs get their full cores, the fastest for a single user on real data: 77 minutes against 99 for the 108-tool matrix. Its limits are the 24-core cap, which serialises concurrent users, and Galaxy sharing the node with the jobs, which failed under four users. Give flye and similar tools enough memory to avoid the OOM kills.
  2. For several concurrent users, use Batch without a pool, and move the data off the head node. Batch held four users to a 10% wall-clock increase. Its cost per user falls from $3.41 to $2.90 and its remaining inefficiency is the NFS tax: I/O-bound tools run 1.7 to 4 times slower on a Batch VM than on local disk and slow further as users are added. An object store or a faster shared filesystem for job inputs is the single largest improvement available to the Batch configuration.
  3. Turn the warm pool off. On the tool tests the current 120 s and 2 pays about $2 over no pool for no gain. On real jobs the recommended 600 s and 4 reused a third of jobs and saved 15 to 20 s of median wait while adding 40 to 57% to the Batch bill, with the same wall-clock. There is no setting at which it paid for itself.
  4. Raise the local runner's worker count. Uploads queue behind 12 workers in every configuration and that queue, not tool execution, sets the pace of the test step.
  5. Give GPU jobs a fallback. When g2 capacity is exhausted the pooled runner waits indefinitely. A claim timeout that also covers VMs that never reach running, or a fallback to the CPU destination, would have saved 25 minutes and five failures.
  6. Check the core allocation of any destination before comparing it. The quarter-core CPU request on the Kubernetes destination silently gave the no-Batch configuration a quarter of its threads for two days of experiments. The galaxy_slots job metric shows what a job really got; compare it across destinations before trusting a timing.
